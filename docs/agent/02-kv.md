# 2. Keys and values

Everything under `/v1/kv/{key}`. The key is the decoded path after the prefix, so
`/v1/kv/orders/42/state` addresses `orders/42/state`. Keys are hierarchical only in the sense that
`/` is an ordinary character you can use as a separator.

## Reading

```bash
curl -s -X GET localhost:8500/v1/kv/service/leader              # JSON envelope, value base64
curl -s -X GET 'localhost:8500/v1/kv/service/leader?raw'        # the bytes
```

Every read answers with the key's version in `X-DisCas-Version`, including a `404`. So does every
write -- a commit has a version whether or not it was fenced:

```bash
curl -s -D - -X GET -o /dev/null localhost:8500/v1/kv/service/leader
```
```
HTTP/1.1 200 OK
X-DisCas-Version: 31333a32
```

That is the same version `?cas=` fences a write on and `?version=` watches from
([3](03-watch.md)) -- you get it from the read you were making anyway, with no extra call.

A missing key is a `404` either way, but the shape differs, because a response's content type is
fixed before the answer is known:

```bash
curl -s -X GET -w ' [%{http_code}]\n' localhost:8500/v1/kv/absent
```
```json
{"error":"not found"} [404]
```

Under `?raw` the same miss is a **bodyless** `404` -- an `application/octet-stream` response is not
the place for a JSON error.

Reads are **linearizable**: the coordinator runs a full consensus round, so the answer reflects a
state a quorum agreed on. That costs what a write costs.

### `?stale`

```bash
curl -s -X GET 'localhost:8500/v1/kv/service/leader?raw&stale'
```

Answered from one node's own committed state: no round, no waiting on a quorum. Cheaper, and it
**still answers when the cluster has lost quorum** -- at the cost of possibly being behind.

Use it for read-heavy paths that tolerate that. Do not use it to decide anything, and never before
taking a lock.

## Listing keys

```bash
curl -s -X GET 'localhost:8500/v1/kv/?keys'
```
```json
["jobs/nightly","service/leader","watched"]
```

Any path is a prefix filter, pushed down to the nodes so each walks only the matching range:

```bash
curl -s -X GET 'localhost:8500/v1/kv/service?keys'
```
```json
["service/leader"]
```

**Keys only, never values.** A listing reports what nodes have *accepted*, and an accepted-but-not-
chosen write can still be superseded -- so a key mid-write on a minority may appear and later vanish.
Read a value with `GET` when you need a committed one.

By default a listing needs a majority to answer and **fails** below it, rather than silently
returning a short list. Note the status when it fails -- it is a `500`, not a `503`:

```json
{"error":"Scan did not reach quorum (1 of 3 configured nodes responded, quorum is 2)"} [500]
```

`?keys&stale` opts into a best-effort listing instead: whatever answered, even below a majority.
Right for an operator looking at a broken cluster, wrong for anything that acts on the result.

A listing always says how far it can be trusted, in headers -- the body stays a bare array of keys:

```bash
curl -s -D - -X GET -o /dev/null 'localhost:8500/v1/kv/?keys&stale'
```
```
HTTP/1.1 200 OK
X-DisCas-Complete: false
X-DisCas-Responded: 1
X-DisCas-Cluster-Size: 3
```

`X-DisCas-Complete` is the question worth asking: `true` means every key committed before the scan
started is in the list. It can only be `false` under `?stale`, since that is the only way a listing
comes back below a majority at all. The two counts are the evidence behind it, so a `false` says
*how* short the answer is rather than merely that it is.

> `?stale` means two different things, matched to the axis each endpoint has. On a single-key read
> it is about **freshness** of one key. On a listing it is about **coverage** of the key set. Both
> spell the same idea -- *an incomplete answer beats none here*.

## Writing

```bash
curl -s -X PUT --data-binary 'node-9' localhost:8500/v1/kv/service/leader
```
```json
{"ok":true}
```

`POST` does the same thing as `PUT`. The body is the value; there is no length limit below the
cluster's own, and a body over it is a [`413`](06-errors.md).

That is the **unfenced** write: it overwrites whatever is there. It is the right call when you are
the only writer, and the wrong one the moment you are not.

## The conditional write: `?cas`

This is the part worth reading twice.

A conditional write here compares the key's **version**, never its bytes. The version travels as an
opaque version in the `X-DisCas-Version` response header, which every read carries:

```bash
curl -s -D - -X GET -o /dev/null 'localhost:8500/v1/kv/service/leader'
```
```
HTTP/1.1 200 OK
X-DisCas-Version: 313a33
```

Then write against it:

```bash
curl -s -X PUT --data-binary 'node-9' 'localhost:8500/v1/kv/service/leader?cas=313a33'
```
```json
{"swapped":true,"value":"bm9kZS05"}
```

Come back later with the same, now stale, version and it is refused:

```bash
curl -s -X PUT --data-binary 'node-11' 'localhost:8500/v1/kv/service/leader?cas=313a33'
```
```json
{"swapped":false,"value":"bm9kZS05"}
```

`value` is the value in force afterwards, base64, and the reply carries the resulting
`X-DisCas-Version` **whether or not the swap took** -- so a caller that lost the compare recomputes
from the version that won without a second read.

**Losing the compare is a result, not an error.** It arrives as `200` with `"swapped":false`.

### `swapped` means "it holds what you asked for"

Not "this call changed it". Writing the value that is **already there** is recognised as a no-op:
the cluster confirms a quorum still agrees, skips the write, and answers `"swapped":true` with the
**version unchanged**.

```bash
curl -s -D - -X PUT --data-binary 'X' 'localhost:8500/v1/kv/idem?cas=313130353a33'
```
```
X-DisCas-Version: 313130353a33      <- the same version you sent
{"swapped":true,"value":"WA=="}
```

Three consequences worth holding on to:

- **A version stays valid across an identical write**, so replaying one keeps answering `true`. That
  is not a fence failure -- nothing happened, twice.
- **An identical write is cheap.** It costs a prepare and no accept broadcast.
- **A watch does not fire for it** -- see [3](03-watch.md). If your value carries a timestamp or a
  nonce it will never be identical, and none of this applies.

### Create-if-absent

```bash
curl -s -X PUT --data-binary 'v1' 'localhost:8500/v1/kv/new/key?cas=0'
```
```json
{"swapped":true,"value":"djE="}
```

`cas=0` means *the key has no committed value*. Run it again and you get `"swapped":false` with
whoever won. It is unambiguous against a real version because a version is hex pairs and `0` is not.

### There is no value-compared form

```bash
curl -s -X PUT --data-binary 'x' 'localhost:8500/v1/kv/new/key?cas'
```
```json
{"error":"?cas needs a version: ?cas=<X-DisCas-Version value>, or ?cas=0 for create-if-absent. There is no value-compared form."} [400]
```

Refusing is the point. Silently promoting a bare `?cas` to an unconditional write would apply a
write whose precondition the caller believed was being checked. A value-compared CAS cannot be made
safe under ABA -- [why](../dev/03-caspaxos.md#version-fenced-cas-and-no-value-compared-cas).

### Read-modify-write

The loop is: take a version, compute, write against it, and on `"swapped":false` recompute from what
came back rather than re-reading.

```bash
read_version() {
  curl -s -D - -X GET -o /dev/null "localhost:8500/v1/kv/$1" \
    | tr -d '\r' | awk -F': ' '/X-DisCas-Version/{print $2}'
}

ver=$(read_version counter)
curl -s -X PUT --data-binary '1' "localhost:8500/v1/kv/counter?cas=$ver"
```

Never re-send a version you already know is stale.

## Deleting

```bash
curl -s -X DELETE localhost:8500/v1/kv/service/leader                   # unfenced
curl -s -X DELETE 'localhost:8500/v1/kv/service/leader?cas=393a33'      # fenced
```

The unfenced form answers `{"ok":true}`; the fenced one answers like a fenced `PUT`, with `swapped`,
`value` and a version:

```json
{"swapped":true,"value":null}
```

A fenced delete is exactly a CAS to a tombstone, and it matters for the same reason: an unfenced
delete left indeterminate can land *after* a later writer has recreated the key.

The key is tombstoned rather than removed, so a replica that missed the delete cannot resurrect the
old value. Tombstones are collected later, automatically.

## Why the fenced forms

Both fenced forms exist for one reason, and it is the same reason: **a duplicate of a fenced write
provably cannot apply twice**, because it carries a version the register has already overtaken. That
is what makes it safe to re-send when a coordinator stops answering -- which is exactly the situation
[6](06-errors.md) is about.
